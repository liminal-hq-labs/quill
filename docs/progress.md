### T1

Run with `win16/tools/run-w31.sh` (DOSBox-X 2025.02.01 in Docker, Xvfb, `machine=svga_s3`, `cputype=pentium`, Windows for Workgroups 3.11 in 386 Enhanced mode, `GetWinFlags=00000C29`). Logs: `docs/evidence/t1-probe-parent.log` and `t1-probe-child.log`. A second copy of the program, started with `WinExec`, yields in a loop with other patterns while the first runs every case.

- **A task switch leaves the other task's high halves in EBX, ESI, EDI and EBP.** Raw calls to `Yield`, `PeekMessage`, `GetMessage` and `DialogBox` returned `ESI=6666BE02` to a task that loaded `2222BE02`: the low half is restored, the high half belongs to the task that ran meanwhile. The child lost all four high halves about 150,000 times in 326,000 rounds. Through the runtime's import stubs, which push and pop the full 32-bit EBX, ESI, EDI and EBP, there were 0 changes in the parent's five cases (twice, with FS and GS set and clear) and 0 in the child's 163,000 stubbed rounds. So the stubs are required and enough; every exported-procedure wrapper must save the four registers too (the template's `export_proc!` does).
- **EBX is scratch in every API,** low half included (`GlobalAlloc`, `PeekMessage`, `GetMessage`, `DialogBox`, `SendMessage` all return a different EBX).
- **FS and GS do not survive** calls that enter the memory manager or the message loop (`GlobalAlloc`, `PeekMessage`, `Yield`, `GetMessage`, `DialogBox` give 0). `GetVersion` and a 12-million-iteration busy loop under timer interrupts keep them. So the far-memory helpers load FS or GS inside each helper and never hold them across a call, as `toolchain-needs.md` says.
- **ESP's high half becomes 0x8001** after the first message-loop call and stays there. It is harmless on a 16-bit stack and the stubs clear it (`movzx esp, sp`).
- **`SendMessage` to Program Manager** (another task, 16-bit code) leaves ESI, EDI and EBP alone: only a target task that uses the high halves leaks.
- **Jump tables:** a four-way `match` compiled to `jmp [ebx*4+0x10]` and its entry landed on `0001:11D0`, the middle of a `call`, which Windows reported as an illegal instruction. Jump tables are off in `win16/.cargo/config.toml` until the cause is found (the table is in the data segment while its entries are code offsets; the packer or the linker script is the suspect). T2 should look at it before multi-segment code, since a jump table inside a segment is exactly the case the plan calls safe.
- A screenshot of the fault dialog on a real Windows 3.11 desktop is in the scratch directory only; the committed screenshots start at M5.

### What the Win16 build needs from this work

- **Core.** Everything under `crates/quill-app` is shared: list Backspace and joins, fields in the body, `pos_at_point` and the selection helpers, `RecentList` and `shorten_path`, `accel::from_vk` (the virtual-key codes are the same on Windows 3.1), `command_tip` and `command_hint`, `Command::Zoom`, and the menu tree's `rule` and `sub` fields. A Win16 menu that ignores `rule` and `sub` keeps working: `Item::command` of a submenu item is its first entry's command.
- **Settings.** Use `each_setting` and `apply_setting` with `GetPrivateProfileString` and `WritePrivateProfileString` on `QUILL.INI`, leave the recent-file section at its default name `Recent` (the Win32 build sets `Recent32`), and do not turn on the `long-names` feature (names stay 64 bytes).
- **Save As.** COMMDLG.DLL on Windows 3.1 has no Explorer style and no `CDN_TYPECHANGE`. Its old-style dialog sends a hook `WM_COMMAND` with `CBN_SELCHANGE` for the type list (`cmb1`, id 0x470) and holds the name in the edit box `edt1` (id 0x480), so the same rule (swap the extension, keep the name) can be done in an `OFN_ENABLEHOOK` procedure by reading and writing `edt1` with `GetDlgItemText` and `SetDlgItemText`. Not tried on Windows 3.11; with no hook, `lpstrDefExt` only adds an extension to a name typed without one.
- **Menus.** The Win32 menu is rewritten after each command to show the recent files; the Win16 build can do the same with `InsertMenu` and `DeleteMenu` (both in USER.EXE), numbering the items `&1` to `&4`.

### Spelling as you type (measured)

The SPEC plans a wavy red underline, drawn in idle time for the visible paragraphs (§ Spelling), off by default on Win16 and on elsewhere; the roadmap lists it for Win16 as a later item. It is not built on any platform yet. Cost, from `cargo test -p quill-spell --release --test real lookup_cost -- --ignored --nocapture` on a Ryzen 7 7700X: a lookup of an 8-letter word in `EN_CA.DIC` takes about 600 ns (about 2,700 cycles) and a misspelt one about 1,300 ns, with the dictionary in `HeapStore` chunks. A 486 does the same work in perhaps 10,000 to 15,000 cycles (no superscalar issue, a small cache for a 300 KB table), which is about 0.2 ms a word on a 486DX2-66 and under 0.1 ms on a Pentium 90; a full visible page of 500 words is about 100 ms on the 486 and a typed word checked as it ends is a fraction of a millisecond. The repaint is a short zig-zag drawn under each unknown word with `LineTo`, a few dozen pixels, next to text drawing that already costs more per word. So the idle-time design in the SPEC is affordable: check the words of the caret's paragraph after a pause, cache the result per paragraph until it changes, and draw the underline in the same off-screen paint. What would hurt on a 386 or 486 with 4 MB is the dictionary: reading 300 KB at first use (about a second from disk) and keeping it resident. Not measured: DOSBox-X at a fixed cycle count (the DOS build's F7 path was not timed there), real hardware, and the repaint cost on a real display.

## Assumptions

D58 to D69 in [decisions.md](decisions.md) were made while implementing; each stands until the owner confirms or changes it.

### The Win16 fault: the high half of ESP

A ToolHelp fault handler (`win16/src/fault.rs`, `InterruptRegister`) logs every register at the fault; `docs/evidence/win16-fault.log` is the record from Windows for Workgroups 3.11 under DOSBox-X: `ESP=800187FC`, `ESI=80018818`, `EDI=00000005`, `EBP=00000023`, with DS, ES and SS all 1207 and the frame starting `2556 11EF`. The register that `rep movs` used was ESI, built by `lea esi,[esp+x]`, and it carries the high half of ESP, 0x8001. That is what the Win16 installer agent found (`retro-win16.md`, D74 in liminal-installer): the high half of ESP is left dirty at every timer tick, and code16 addresses the stack through ESP with the address-size prefix, so any `[esp+x]` or `lea r,[esp+x]` after a tick reads or builds an address above the segment limit. Ruled out here: stack depth (12 KB above its floor, and the fault moves with DGROUP layout only because a different layout changes how long the code runs between API calls), ES, DS, SS, DF, and jump tables (off). The faults were deterministic in appearance only because the same function ran long enough to be hit.

What would close it, in the order to try: (1) frame pointer plus a `movzx esp, sp` at every function entry, and `[ebp+x]` for locals and arguments (EBP stays clean once set, since the dirt is made only in ESP), done by rewriting the assembler the build produces (`--emit=asm` with LTO gives one file) before it is assembled; (2) the same `movzx esp, sp` before every instruction that has an ESP operand, at a cost of four bytes each; (3) running long computations between API calls, which the import stubs already clean after. The multi-segment packer being built in `rust-win16` should carry the fix, because it owns the build's last step.

### The shared packer: the fault is gone, and a different bug shows

`win16/` now carries the multi-segment packer and 32-bit-stack runtime of `rust-win16` (branch `feat/multi-segment`, commit 4c0bac4; `win16/PROVENANCE.md` lists the changes). Rust runs on a 32-bit alias of the stack segment and each import stub switches to the real 16-bit stack, so the dirty high half of ESP never reaches a Rust address. QUILL.EXE builds in six code segments (the packer's `segments.json` places the code by crate and module) and runs the `m1-edit` scenario on Windows for Workgroups 3.11 under DOSBox-X **30 times out of 30 with output equal to the host's golden, byte for byte, and no General Protection Fault** (the loop: `scratchpad/w31loop.sh`; each run is a fresh DOSBox-X session). Before it, runs on the earlier runtime faulted within the first paints. The ESP high half is therefore the cause of the string-instruction faults (D89).

The other thing the runs showed: with the 512-byte staging buffer for the screen dump inside the `PLAY` static, 54 runs of four zero bytes appeared in the dump (the saved `.qld` file was intact), identical in every run. **Cause, found with a canary:** Quill's stack ran past its bottom into the program's statics. `w16_main` built the 13 KB `App::new()` temporary in its own frame, which stayed live for the whole run, so the deepest calls (`snapshot`, `draw`, layout) needed about 36 KB of a 30 KB stack, and their frames landed on `PLAY`, `STORE` and the log buffers. The packer's runtime and the alias were not involved: the same holes appeared with the alias off, the packer agent's 512-byte stack-buffer test found nothing, and a standalone reproducer (`win16/examples/stackprobe`) found nothing in 20 runs with the alias and 19 without. How it was found: 512 bytes of 0xAA were put after `PLAY` and checked at every `FarStore` call and message; the first change came between two store calls inside `draw`, which pointed at the stack, and `0x7800` of stack plus a 4 KB heap failed while `0x9000` plus 1 KB passed, with the same code. The fix: `App::new()` is built in an `#[inline(never)]` function, so its temporary is gone before the message loop (the 13 KB is no longer live), and the original sizes stay. The staging buffer is back inside `PLAY` (the workaround is removed). A play-back now writes `STACK.LOG` (`stack used 22988 of 30720 margin 6492`) and `win16/tools/check_stack_log.py` fails when the margin is under 2 KB; `quill-host/tests/size.rs` keeps `App` under 16 KB on the host. The `m1-edit` run on Windows 3.11 matches the golden with no holes.

The first 30 runs above used the workaround build; the fixed build (stage back in `PLAY`, `init_app`, the original stack and heap) then ran the `m1-edit` scenario 12 times on Windows 3.11 with all 12 outputs equal to the host's golden and a stack margin of about 6.5 KB.

### The Win16 native interface: plan

A session on Windows for Workgroups 3.11 found four faults in `QUILL.EXE` from `feat/m5-win16`: the window shows the DOS text screen in a Windows frame; nothing typed shows; Help > Contents says "Cannot open Help file."; the minimised window has no icon. Causes, found before any change: `InvalidateRect(hwnd, 0, 1)` goes through an import whose rectangle argument is a near pointer, so 0 became `DS:0` (the first bytes of the data segment, an empty rectangle) and no edit was ever repainted; the shared packer copied from `rust-win16` has no `icons` support, so `QUILL.EXE` has no resources at all and `LoadIcon` returns 0; the play harness puts no `QUILL.HLP` on `D:`. The plan, one commit or more per step, each checked on Windows 3.11 under DOSBox-X with screenshots:

1. **Fixes.** A null rectangle for `InvalidateRect`; icons (and bitmaps, and the dialog style names `assets/dialogs/dialogs.json` uses) back in the packer; `win16/build.sh` compiles `QUILL.HLP` beside `QUILL.EXE`; the play harness copies it to `D:`.
2. **Shared view geometry.** The toolbar layout, the ruler's hit testing and drag, the page's place in the window and the status line move into `quill-app` (no platform names, no `alloc`, host-tested), with caret placement and selection by the mouse and scrolling to a line. The Win32 build moves onto them after its open layout change (`fix/win9x-layout`) merges.
3. **The GDI page.** A Win16 `Measure` from `GetCharWidth` and `GetTextMetrics` on a memory DC; the page drawn with TrueType fonts into an off-screen bitmap and copied with one `BitBlt`; narrow invalidation; a vertical scroll bar; the window placed and sized for a 640 by 480 screen; a status bar; the mouse places the caret and selects. The text view stays only for `/PLAY`, so the golden runs still compare Windows 3.11 with the host.
4. **Chrome.** The two toolbar rows (glyphs from `assets/toolbar/toolbar.bmp` as a bitmap resource), the style, face and size combo boxes, and the ruler.
5. **Dialogs.** About, Find and Replace, Fonts, Tabs and Spelling from `assets/dialogs/dialogs.json` through `DialogBox`; the unsaved-changes question as a message box; Open, Save As and Insert Picture through `COMMDLG.DLL`, and Print Setup through `PrintDlg`.
6. **Stack and size.** Every step keeps the stack guard (`check_stack_log.py`) and the segment budgets; the data segment holds the data, a 29 KB stack and the local heap in 64 KB.

### The Win16 native interface: where it stands

Steps 1 to 5 of the plan are done; each was checked by hand on Windows for Workgroups 3.11 under DOSBox-X (VGA, 640 by 480), driven with `xdotool` on a private Xvfb display:

- **Typing and the mouse.** `LETTER.RTF` drawn with its fonts, text typed at its end, a drag selecting across lines (`docs/media/win16-typed-selection-w311.png`); the cause of "nothing typed shows" was `InvalidateRect(hwnd, 0, 1)` passing `DS:0` as the rectangle.
- **Chrome.** Both toolbar rows, the style, face and size boxes, the ruler with a tab stop set from the Tabs dialog (`win16-format-bar-w311.png`).
- **Dialogs.** About (`win16-about-w311.png`), Replace All (`win16-replace-all-w311.png`), Spelling with `EN_CA.DIC` (`win16-spelling-w311.png`), the unsaved-changes question (`win16-unsaved-question-w311.png`), COMMDLG's Open (`win16-open-commdlg-w311.png`) and Font (`win16-choosefont-w311.png`); Save As wrote `SPELL2.QLD`, Insert Picture took a PNG, Print Setup reached COMMDLG's "No default printer".
- **Help and icon.** F1 opens `QUILL.HLP` from beside `QUILL.EXE` in the real WINHELP.EXE (`win16-help-contents-w311.png`); minimised, the window shows the Q (`win16-minimised-icon-w311.png`), and Alt+Tab shows it too (`win16-alt-tab-w311.png`).
- **Golden play-back.** The `m1-edit` scenario under `/PLAY` gives frames and a saved `PLAIN.QLD` byte-identical to the host's.
- **Stack and size (step 6).** `STACK.LOG` after the longest hand session (every dialog): 24,278 of 30,720 bytes used, 3,674 to spare, above `check_stack_log.py`'s 2 KB floor. The largest code segment is 56,390 bytes. The data segment is full: 30,032 bytes of data, the 30,720-byte stack and a 4,096-byte local heap leave 688 bytes of the 64 KB, so the next static that grows needs the stack or heap to give way, or data moved to far memory.
