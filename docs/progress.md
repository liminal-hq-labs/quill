## Evidence

### RTF code pages (U0)

- Host: `tests/rtf/*.rtf` with `.expect` files (1250, 1251, 1253, 1254 and 1257 documents, mixed fonts, `\u` with `\uc` and surrogate pairs, double-byte text) give the expected Windows-1252 text and exact counts; all 224 Windows-1252 characters round-trip through `\u`; 768 table entries equal Python's codecs (`crates/quill-text/tests/data/codepages.tsv`, rewritten by `scripts/gen-codepages.py`, which also builds the Win16 resource and checks it with `--check`); property tests on damaged escapes. Every existing golden is unchanged (`make validate`).
- Windows 3.11 (DOSBox-X, `win /3 D:\QUILL.EXE D:\CP1254.RTF`): the Turkish fixture opens with `ğ`, `ı` and `ş` as `?`; with the resource missing they would have been `ð`, `ý` and `þ`. `e2e-launch-w31.sh` passes with the same stack margin (9,350). `\u` and the Win16 data segment: the resource is found with `FindResource` and read through its far pointer.
- Not run: `make dos` (the DOSBox install and uninstall) and `make win32` (the Wine install); `QUILLDOS.EXE` and `QUILL32.EXE` were built, and the Win32 import and Pentium scans pass. The tables reach those builds through `quill-text`'s own default, which the host tests cover.

### M0

- `make validate` passes: format, clippy with the portable-crate lint set, 16 tests under `cargo nextest`, headers, float ban.
- Property tests against a `Vec` and a `String` model run with 8-byte and 96-byte chunks, so every few operations cross a chunk edge: after any edit sequence the text and both format layers match the model, undoing every step reaches each earlier state, redoing reaches each later one, and an out-of-memory failure leaves the text as it was.
- `tests/docs/plain.qld` is built by `quill-host`'s `make-docs`, read back, laid out with `GridMeasure` and compared with `tests/golden/layout/plain.grid.txt`; read then write gives the same bytes.
- `tests/golden/pages/plain.grid.png` is the page map (see D61).

### T4

- `make dos` (or `dos/tools/e2e.sh`) builds `QUILLDOS.EXE` (about 34 KB, CWSDPMI inside) with the pinned toolchain and no C compiler, runs it under headless DOSBox Staging 0.83.0 at `cputype = 486`, and compares the screen it read back from video memory (B8000h) with `tests/golden/screens/hello.80x25.txt`: identical, characters and attributes.
- The DOS side needs `-Zbuild-std` through `RUSTC_BOOTSTRAP=1`, as Desk does; it is not part of `make validate`, which stays host-only.

### M2 (partly)

- **RTF.** `quill-formats/src/rtf.rs` reads the subset (characters, paragraphs, tab stops with kinds and leaders, page setup, font and colour tables, `\'hh`, `\uN`, the named punctuation) and skips every other destination; it writes the canonical subset. `tests/rtf.rs` checks the hand-written `tests/docs/letter.rtf`, that write, read, write is stable, tolerance of unknown words and destinations, refusal of non-RTF and of control words over 32 characters, and 300 damaged or truncated variants of the letter for panics and leaks.
- **LibreOffice.** `scripts/check-rtf-libreoffice.sh` (also run on `tests/docs/pictures.rtf`, which adds the count of images, 2) reads `letter.rtf`, writes it with Quill, converts both to HTML with `soffice --headless`, and requires the same text and the same counts of bold, italic, underline, strike, superscript, subscript, centred, right, justified, red text, Arial and Courier runs. It passes (3 bold, 1 of each of the others).

### DOS runtime: directories, drives and rename

`dos/rt` gained `find_first`, `find_next` and `find_each` (INT 21h 4Eh and 4Fh through a DTA in conventional memory), `current_drive`, `set_current_drive`, `current_dir`, `drive_attributes` and `drive_valid` (IOCTL 4409h), `logical_drive_map` (440Eh), `floppy_count` (INT 11h), `drive_mask`, `rename` (56h), `set_attributes` (4301h), `dos_version` (30h), `dpmi::free_memory` (0500h) and an INT 24h critical-error stub (`install_critical_handler`). `dos/tools/rt-test.sh` builds `RTTEST.EXE` and runs it under headless DOSBox Staging 0.83.0 on a prepared C: (`make dos` runs it):

- `RTTEST list` reads a tree of 1149 entries back (folders, a folder of 600 files and one of 512, a path 12 levels deep, names in lower, upper and mixed case, punctuation that sorts differently by case) and its output equals the host's upper-cased, sorted listing, line for line.
- `RTTEST self` passes 23 checks: C:, D: and Z: valid; E: refused with error 0Fh; find and open on E: fail at once with no hang; rename, rename onto an existing name (refused), rename of a missing file (error 2) and a move into a folder; the INT 24h vector points at the stub, the stub's bytes are `B0 03 CF`, the old vector comes back on removal and when the exit list runs.

What DOSBox Staging 0.83.0 does, from `RT_PROBE=1 dos/tools/rt-test.sh`:

- **`.` and `..` are returned** for every folder with mask 10h, **including the root of a mounted drive**, where real DOS returns neither. A dialog must decide "below the root" from the path, never from the presence of `..`.
- **Order is not byte order.** Within a folder the entries come out alphabetical by 8.3 name (`A-B.TXT`, `A.TXT`, `A1.TXT`, `A_B.TXT`, `A~1.TXT`), but a drive's root lists folders first, then files. Real DOS gives directory order. The core sorts, as the plan says.
- **Attribute masks.** With mask 0 only normal files return; mask 10h adds folders. A file made hidden with 4301h is not returned with mask 0 or 10h and is returned with mask 02h. Volume labels never appeared. A host file with mode 444 shows as attribute 21h (read-only, archive); ordinary files show 20h.
- **Host names that are not 8.3 are shortened, not hidden:** `verylongfilename.txt` is `VERYLO~1.TXT`, `has space.txt` is `HASSPA~1.TXT`, `ok.html` is `OK~1.HTM`, `tw.o.dots` is `TW~1.DOT`, and `.dotfile` is not listed. Lower and mixed case come back in upper case. These are DOSBox's aliases and are not the host names, which is another reason to refuse rather than truncate.
- **Errors:** a missing folder and a file used as a folder give 3; a missing file in an existing folder gives 12h (not 2), and a wildcard that matches nothing gives 12h too (`find_each` reports it as zero entries).
- **Drives.** 4409h answers `Ok` (attribute word 0802h) for A:, B:, C:, D:, Y: and Z: and error 0Fh for E: to X:. **A: and B: are valid although no floppy is mounted and `INT 11h` reports 0 floppies**, so `drive_mask` leaves A: and B: out beyond the floppy count. Y: is valid in this DOSBox (an extra drive it provides); Z: reports 0 bytes free. 440Eh answers 1 for A: and B: (one device with two letters) and 0 for the rest. C: and D: report 256,000 KB free (DOSBox's default for a mount). `set_current_drive` returns 26. DOS reports version 5.0.
- **A drive that is not ready cannot be made in DOSBox**, so the INT 24h stub is proven only to install, hold the right bytes, restore the old vector and be removed by the exit list. That DOS calls it, and that it makes the call fail rather than show "Abort, Retry, Fail", is not tested, and neither is it under CWSDPMI with a real floppy.
- **`CWSDPMI.SWP`** appears in the program's folder (here the root of C:) when a DPMI client runs, so a directory listing of the program's own folder contains it.
- **Free memory:** DPMI 0500h reports a largest block of about 148 MB with `memsize = 16`.

Timings, `cputype = 386`, `core = normal`, `cpu_cycles = 3000` and `cpu_cycles_protected = 3000` (a 386SX-class machine, as `docs/testing.md` describes), set through `DOS_CONF` after the generated `[cpu]` section (a second section overrides the first: the program finds it cannot set the AC flag, which a 386 cannot, and the times are 20 times longer than with `cpu_cycles = max`). The BIOS tick counter has a 54.9 ms resolution, so each case runs for 40 ticks or more. Emulated time is deterministic: three runs gave the same numbers. `RT_TIME=1 dos/tools/rt-test.sh` reproduces them.

| Read | Entries | Reads | Per read | Per entry |
|---|---|---|---|---|
| Find first and next over a folder of 600 files | 602 (with `.` and `..`) | 17 | 132 ms | 220 us |
| The same over 512 files | 514 | 19 | 116 ms | 224 us |
| A folder 12 levels deep, long path, 5 entries | 5 | 1567 | 1.4 ms | 280 us |
| A walk of the whole tree, with sorting and string building | 1149 | 2 | 1.57 s | 1.36 ms |
| `drive_mask` (26 drive checks) and `current_dir` | 1 | 403 | 5.5 ms | |

With `cpu_cycles = max` the same reads take 4.9 to 6.3 ms for 512 and 600 entries. About 660 cycles per entry is the cost of one DPMI real-mode call plus the Rust that reads the DTA; DOSBox's own directory scan is native code, so a real DOS's scan (and a floppy's seek time) is **not** in these numbers. They bound what the runtime adds, not what a 386's disk costs. A listing of 512 entries is about an eighth of a second of runtime overhead at this speed, which fits the plan's estimate; the floppy-root estimate of a second is untested.

### T1

Run with `win16/tools/run-w31.sh` (DOSBox-X 2025.02.01 in Docker, Xvfb, `machine=svga_s3`, `cputype=pentium`, Windows for Workgroups 3.11 in 386 Enhanced mode, `GetWinFlags=00000C29`). Logs: `docs/evidence/t1-probe-parent.log` and `t1-probe-child.log`. A second copy of the program, started with `WinExec`, yields in a loop with other patterns while the first runs every case.

- **A task switch leaves the other task's high halves in EBX, ESI, EDI and EBP.** Raw calls to `Yield`, `PeekMessage`, `GetMessage` and `DialogBox` returned `ESI=6666BE02` to a task that loaded `2222BE02`: the low half is restored, the high half belongs to the task that ran meanwhile. The child lost all four high halves about 150,000 times in 326,000 rounds. Through the runtime's import stubs, which push and pop the full 32-bit EBX, ESI, EDI and EBP, there were 0 changes in the parent's five cases (twice, with FS and GS set and clear) and 0 in the child's 163,000 stubbed rounds. So the stubs are required and enough; every exported-procedure wrapper must save the four registers too (the template's `export_proc!` does).
- **EBX is scratch in every API,** low half included (`GlobalAlloc`, `PeekMessage`, `GetMessage`, `DialogBox`, `SendMessage` all return a different EBX).
- **FS and GS do not survive** calls that enter the memory manager or the message loop (`GlobalAlloc`, `PeekMessage`, `Yield`, `GetMessage`, `DialogBox` give 0). `GetVersion` and a 12-million-iteration busy loop under timer interrupts keep them. So the far-memory helpers load FS or GS inside each helper and never hold them across a call, as `toolchain-needs.md` says.
- **ESP's high half becomes 0x8001** after the first message-loop call and stays there. It is harmless on a 16-bit stack and the stubs clear it (`movzx esp, sp`).
- **`SendMessage` to Program Manager** (another task, 16-bit code) leaves ESI, EDI and EBP alone: only a target task that uses the high halves leaks.
- **Jump tables:** a four-way `match` compiled to `jmp [ebx*4+0x10]` and its entry landed on `0001:11D0`, the middle of a `call`, which Windows reported as an illegal instruction. Jump tables are off in `win16/.cargo/config.toml` until the cause is found (the table is in the data segment while its entries are code offsets; the packer or the linker script is the suspect). T2 should look at it before multi-segment code, since a jump table inside a segment is exactly the case the plan calls safe.
- A screenshot of the fault dialog on a real Windows 3.11 desktop is in the scratch directory only; the committed screenshots start at M5.

### Spelling as you type

Built on the Windows 95 build (D201, D202): the scanner is in `quill-app` (`spell_live.rs`) and shared by every build, the wave, the timer and the right-click menu are in `QUILL32.EXE`. It is on by default there and off in the others; DOS text mode and Windows 3.x do not use it yet.

- **How it runs.** After a key, a click, a scroll or a command, a 300 ms timer arms; when it fires, `spell_idle` checks six words of the lines on the screen and says whether more is left, at the system's 55 ms step, and the timer stops when nothing is left. No work happens while typing: each key restarts the wait. The marks (64 at most, 8 bytes each) live in one `Store` chunk; the scanner's own state is 76 bytes. The changed lines are painted again once every four batches and at the end.
- **Checked by.** 9 host tests in `crates/quill-host/tests/spell_live.rs` (one is a property test of random typing, moving, undo, scrolling and idle calls: the marks are in order, apart, inside the document, on whole words, and equal what F7 stops at once the scanner is done) and the `m10-spell-live` scenario; `win9x/tools/wine-spell-live.sh` (pixels under Wine at Page Width and 100 percent); `win9x/tools/w95-spell-live.sh` (pixels on a real Windows 95 in DOSBox-X: no red under correct text or under the word being typed, a wave 2 to 3 pixels deep under each finished misspelling, the menu from the right button and from Shift+F10, the first suggestion taking its wave away, and Find > Check Spelling as You Type ticked, hinted and switching the marks off). Screenshots: `docs/media/spell-live-win95-*.png`.
- **Cost on the host.** About 1.35 µs a word for the whole idle path with the real `EN_CA.DIC` (`cargo test -p quill-host --release --test spell_live idle_cost -- --ignored --nocapture`, a Ryzen 7 7700X, 360 words a page).
- **Cost in DOSBox-X** (Windows 95 OSR2.5, Pentium core, `cycles=fixed N`, `QUILL32.EXE` with timing hooks from `win9x/tools/spell-bench.patch` and `win9x/tools/w95-spell-bench.sh`; 252 words of 12 point text on the screen, two misspelt in each sentence of 19 words; 14 keys typed 2 s apart at 12000 cycles and 6 s apart at 3000). By DOSBox's rule of thumb 3000 cycles is a 386SX and 12000 a 486DX-33.

| | 12000 cycles (486DX-33) | 3000 cycles (386SX) |
|---|---|---|
| Dictionary read, once (`EN_CA.DIC`, 300 KB) | 0.27 s | 0.97 s |
| Idle check, a word | 2.7 ms (369 words a second) | 11.5 ms (87 words a second) |
| One batch of six words | 16 ms (longest 21 ms) | 67 ms (longest 88 ms) |
| First scan of the screen, 252 words, start to end | 8.3 s (30 words a second) | 25.7 s (9.8 words a second) |
| After typing a word: its rescan, mean (longest) | 3.9 ms (8.2 ms) | 16 ms (34 ms) |
| One full paint of the page (feature off, mean) | 0.82 s | 3.4 s |
| Key to the end of its repaint, feature off, median of 13 | 1.067 s | 4.418 s |
| Key to the end of its repaint, feature on, median of 14 | 1.118 s (+4.8 percent) | 4.640 s (+5.0 percent) |

- **Reading it.** The lookups are not the cost. A word takes 2.7 ms at 12000 cycles (about 33,000 instructions; the host does it in 1.35 µs), so a six-word batch is 16 ms, and the rescan of a word just typed 4 ms. Painting is the cost: one full paint of the page takes 0.82 s at 12000 cycles and 3.4 s at 3000, and that is the editor's own price for every key (each paint lays the document out more than once and fills the text grid). So the checker's paints are few (the changed lines once for four batches and at the end of the scan) and each draws only the lines that reach into the damaged rectangle, and the first scan of 252 words takes 8 s at 12000 cycles and 26 s at 3000, most of it the timer's 55 ms steps and those paints. No check runs while keys come in (each key restarts the 300 ms wait), so the only cost a key sees is the extra drawing of the waves and the mark bookkeeping: its time to the end of its repaint is about 5 percent more with the feature on, at both speeds. A key that arrives in the middle of a batch waits for it (16 ms, or 67 ms at 3000 cycles). I did not type by hand: by these numbers typing is no more delayed by the checker than by the 5 percent, and it is slow in both cases at these speeds, because the page repaint behind every key is a second or more (the first sample of each key log, 41 to 47 s, is the open dialog's keys waiting for the first paint and is left out of the medians).
- **Not proven.** Real hardware; a slower machine than 3000 cycles; Windows 98 or Me; scrolling during a scan of a document of several screens (host tests only); the 1 second dictionary read on a real 386 or 486 disk (270 ms here from a DOSBox disk image); typing at the speed of a person against the paint costs above (the harness types one key in 2 s or in 6 s so that every key is repainted alone); the Win16 build with the feature compiled in has not been run (see below).

**DOS text mode, to do.** The scanner needs nothing new. The text painter asks `spell_marks(store, line_start, line_end)` for each row and gives the cells inside a mark the SPEC's attribute (red background in colour, reverse in mono) instead of a wave. The DOS main loop gives the idle call its turn when `INT 16h` AH=01h finds no key: `spell_set_view` from the first and last visible row's line (the painter knows them), `spell_idle(store, 8)`, and stop asking once it returns false; a key restarts the wait (the BIOS tick at `0040:006C` is the clock; no timer is needed). The dictionary is read the first time (`spell_live_ready`), so a floppy machine waits for it once: say so on the status line. The default is off until the read has been timed on the DOS box; `set_spell_live_default(true)` turns it on. Mark and unmark repaint only the changed rows (`spell_take_changed`).

**Windows 3.x, to do.** The Win16 build compiles the scanner (`win16/build.sh` builds `QUILL.EXE`, code 276,134 bytes against 273,503, every segment inside its budget) but nothing calls it. The data segment is the limit to watch: with the scanner it holds 29,300 bytes of data against 29,080 without it, so 2,444 of the 2,664 bytes that were free are left (D200 moved the bulk data to far memory). 76 of the 220 are the scanner's state; the rest are the strings of the menu item, its hint and its two messages. The marks are in far memory (`Store`), so the table costs nothing there. `SpellData::user` (2,048 bytes) and the ignore table (768 bytes) could go to a `Store` chunk too if the room is wanted. The shell side is Windows 95's with these differences: `SetTimer`, `KillTimer`, `LineTo` and `MoveTo` (the 16-bit `MoveTo`, no `MoveToEx`) exist in 3.1; `TrackPopupMenu` has no `TPM_RETURNCMD`, so the menu's items post `WM_COMMAND` and the word to change is kept in the shell; there is no `WM_CONTEXTMENU`, so the right button's `WM_RBUTTONUP` and Shift+F10 in `WM_KEYDOWN` open it; and the 300 KB dictionary stays resident, which on a 4 MB machine is the reason the SPEC leaves it off by default.

### The Win16 fault: the high half of ESP

A ToolHelp fault handler (`win16/src/fault.rs`, `InterruptRegister`) logs every register at the fault; `docs/evidence/win16-fault.log` is the record from Windows for Workgroups 3.11 under DOSBox-X: `ESP=800187FC`, `ESI=80018818`, `EDI=00000005`, `EBP=00000023`, with DS, ES and SS all 1207 and the frame starting `2556 11EF`. The register that `rep movs` used was ESI, built by `lea esi,[esp+x]`, and it carries the high half of ESP, 0x8001. That is what the Win16 installer agent found (`retro-win16.md`, D74 in liminal-installer): the high half of ESP is left dirty at every timer tick, and code16 addresses the stack through ESP with the address-size prefix, so any `[esp+x]` or `lea r,[esp+x]` after a tick reads or builds an address above the segment limit. Ruled out here: stack depth (12 KB above its floor, and the fault moves with DGROUP layout only because a different layout changes how long the code runs between API calls), ES, DS, SS, DF, and jump tables (off). The faults were deterministic in appearance only because the same function ran long enough to be hit.

What would close it, in the order to try: (1) frame pointer plus a `movzx esp, sp` at every function entry, and `[ebp+x]` for locals and arguments (EBP stays clean once set, since the dirt is made only in ESP), done by rewriting the assembler the build produces (`--emit=asm` with LTO gives one file) before it is assembled; (2) the same `movzx esp, sp` before every instruction that has an ESP operand, at a cost of four bytes each; (3) running long computations between API calls, which the import stubs already clean after. The multi-segment packer being built in `rust-win16` should carry the fix, because it owns the build's last step.

### The shared packer: the fault is gone, and a different bug shows

`win16/` now carries the multi-segment packer and 32-bit-stack runtime of `rust-win16` (branch `feat/multi-segment`, commit 4c0bac4; `win16/PROVENANCE.md` lists the changes). Rust runs on a 32-bit alias of the stack segment and each import stub switches to the real 16-bit stack, so the dirty high half of ESP never reaches a Rust address. QUILL.EXE builds in six code segments (the packer's `segments.json` places the code by crate and module) and runs the `m1-edit` scenario on Windows for Workgroups 3.11 under DOSBox-X **30 times out of 30 with output equal to the host's golden, byte for byte, and no General Protection Fault** (the loop: `scratchpad/w31loop.sh`; each run is a fresh DOSBox-X session). Before it, runs on the earlier runtime faulted within the first paints. The ESP high half is therefore the cause of the string-instruction faults (D89).

The other thing the runs showed: with the 512-byte staging buffer for the screen dump inside the `PLAY` static, 54 runs of four zero bytes appeared in the dump (the saved `.qld` file was intact), identical in every run. **Cause, found with a canary:** Quill's stack ran past its bottom into the program's statics. `w16_main` built the 13 KB `App::new()` temporary in its own frame, which stayed live for the whole run, so the deepest calls (`snapshot`, `draw`, layout) needed about 36 KB of a 30 KB stack, and their frames landed on `PLAY`, `STORE` and the log buffers. The packer's runtime and the alias were not involved: the same holes appeared with the alias off, the packer agent's 512-byte stack-buffer test found nothing, and a standalone reproducer (`win16/examples/stackprobe`) found nothing in 20 runs with the alias and 19 without. How it was found: 512 bytes of 0xAA were put after `PLAY` and checked at every `FarStore` call and message; the first change came between two store calls inside `draw`, which pointed at the stack, and `0x7800` of stack plus a 4 KB heap failed while `0x9000` plus 1 KB passed, with the same code. The fix: `App::new()` is built in an `#[inline(never)]` function, so its temporary is gone before the message loop (the 13 KB is no longer live), and the original sizes stay. The staging buffer is back inside `PLAY` (the workaround is removed). A play-back now writes `STACK.LOG` (`stack used 22988 of 30720 margin 6492`) and `win16/tools/check_stack_log.py` fails when the margin is under 2 KB; `quill-host/tests/size.rs` keeps `App` under 16 KB on the host. The `m1-edit` run on Windows 3.11 matches the golden with no holes.

The first 30 runs above used the workaround build; the fixed build (stage back in `PLAY`, `init_app`, the original stack and heap) then ran the `m1-edit` scenario 12 times on Windows 3.11 with all 12 outputs equal to the host's golden and a stack margin of about 6.5 KB.
